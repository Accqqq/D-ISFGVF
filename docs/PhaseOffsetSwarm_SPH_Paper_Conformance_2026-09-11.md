# SPH 协同项论文一致性修复与实测（2026-09-11）

## 1. 结论先说

1. **原来的 SPH 参数确实不对，而且不是"没调好"，是实现和论文不是同一个东西。**
   `h = 10 m`、`rest_density = 1e6`、`gradient` 里带 `C2 = 10*54.97/(7*pi*h^2)`
   这一套是从 SPH-planning 的 `sph/sph.launch` 直接抄过来的。用这组数算出来
   `rho_i ≈ 1.7`、`rho_0 = 1e6`，于是
   `eta_i = (rho/rho_0)^7 - 1 ≈ -1 + 1e-41`，恒等于 $-1$：
   **论文里的密度排斥分支 $\eta^+$ 永远是 0，从来没生效过**，
   吸引分支恒定满幅（但幅值只有 ~1e-2 m/s，同样等于没有）。
   真正剩下的只有 `k_rep/d` 那一项（无界 1/d，没有 `d_rep`），
   在对称队形里几乎完全对消，在贴身时又爆到饱和。
2. 现在 `sph_intent` 已经按论文（`\subsection{SPH Workspace Coordination with
   Path-Tube Preview}`）重写并接上 ROS 参数，9 项新单测 + 36 项原回归全绿，
   整仓编译通过。
3. **实测发现：密度项调大反而把编队压扁。** 同一张无障碍图、15 机、1.5 m 圆盘：

   | k_rho | 机间最小中心距 | 到点 |
   |---|---|---|
   | 0.00（关掉密度项） | **1.293 m** | 15/15 |
   | 0.15（推荐） | **0.964 m** | 15/15 |
   | 0.60（论文形状 + 我最初的取值） | **0.559 m** | 15/15 |

   所以我把默认 `sph/k_rho` 定在 **0.15**。论文里明确写了"常数归一化被吸收进
   协同增益"，也就是说 $k_\rho$ 的具体数值本来就是实现相关的，0.15 不违背论文。
4. 狭窄通道里的 0.06 m 级贴近**不是 SPH 参数能解决的**：1.2 m 宽的通道塞 15 台
   1.5 m 间距的飞机，几何上就不允许。见第 4 节。

## 2. 代码改了什么

### 2.1 `phase_offset_swarm/include/phase_offset_swarm/sph_intent.h`

`SphParameters` 换成论文口径，删掉 `normalization_c / mass / rest_density / k_vis`：

```cpp
double h = 2.0;                  // 核支撑 2h
double reference_spacing = 1.5;  // d*，编队标称间距
double d_rep = 0.9;              // 有界短程排斥激活距离
double gamma = 7.0;              // eta = (rho/rho0)^gamma - 1
double k_rho = 0.15;             // 密度分支增益（实测标定，见第 3 节）
double k_rep = 1.2;              // 有界短程排斥增益
double k_damp = 1.0;             // 相对径向阻尼增益
double g_max = 1.5;              // 总协同速度饱和值 [m/s]
```

输出结构里 `a_i/pressure_i/g_viscosity` 换成 `eta_i/rho_reference/g_damping`。

### 2.2 `src/sph_intent.cpp`

严格按论文实现：

```
rho_i     = 1 + sum_j Wbar(d_ij/h)                 // 自项为 1
rho_0     = 1 + sum_j Wbar(d*/h)                   // 同一可见邻居集、按标称间距取值
eta_i     = (rho_i/rho_0)^gamma - 1
s_i       = sum_j phi(q_ij) n_ij,  phi = -dWbar/dq >= 0
g_den,rep = -k_rho * eta^+ / rho_i * s_i
g_den,att = +k_rho * eta^- / rho_i * s_i           // 只有这一支乘 beta_i
g_rep     = -k_rep * sum_j [1 - d_ij/d_rep]_+^2 n_ij   // 有界，d_rep 外恒 0
g_damp    = +k_damp * sum_j (Wbar(q_ij)/rho_i) ddot_ij n_ij
```

- 短程排斥从无界 `k_rep/d` 换成论文的有界二次式，标称间距处严格为 0；
- 阻尼从"自身绝对速度阻尼"换成论文的相对径向阻尼
  `ddot_ij = (v_j - v_i)·n_ij`，共同平移下恒为 0；
- `rho_0` 用**同一批可见邻居、按标称间距**取值：编队正好处在标称间距时
  `eta_i ≡ 0`，被压紧才是正的、被拉开才是负的。
  （邻居管理器只给 2.45 m 内的邻居，所以实际参与的就是最近一圈。）

### 2.3 参数打通（没有任何新门控）

- `phase_offset_agent.launch` 新增 8 个 `sph_*` arg → `~sph/*` param；
- `agent_state_neighbor_runtime_node` 里读 `~sph/*`，并在启动时打印一行
  `[SIM-C] SPH coordination parameters: h=2 d_star=1.5 d_rep=0.9 ...`；
- `phase_offset_swarm.launch` 新增 `sph_reference_spacing`（0 = 跟随
  `formation_spacing`），orchestrator 把它写进每个 agent 的 include。

### 2.4 测试

新增 `test/sph_intent_test.cpp`（9 项，CMake 已注册）：
标称队形 `eta ≡ 0`；`d < d_rep` 有界排斥且 `d >= d_rep` 严格为 0；
压缩时排斥朝局部聚集的反方向；稀疏时吸引且 `beta` 只作用于吸引支；
相对阻尼对抗相对径向运动、共同平移下为 0；饱和；重合邻居不产生 NaN；
重复 id/非法 beta 关闭输出；`validate()` 强制 `d_rep < d* < 2h`、`gamma > 0`。

结果：新测试 9/9；原 `neighbor_manager 10`、`elastic 7`、`conflict 7`、
`intent 12` 全部通过；`catkin_make` 全仓编译通过。

## 3. 实测（ROS，15 机圆盘，间距 1.5 m，init_y=8，目标平移 -16 m）

统一用只读探针（只订阅 `odom`、`sph_beta`、`g_coord`，绝不订阅 `/uav_i/goal`，
否则会污染 orchestrator 的 goal 连接握手）统计"机间最小中心距"。

| 场景 | k_rho | 机间最小中心距 | 到点 | `g_coord` 有效比例 / 峰值 |
|---|---|---|---|---|
| `phase_offset_open.pcd` | 0.00 | 1.293 m | 15/15 | ~21% / 0.01–0.08 m/s |
| `phase_offset_open.pcd` | 0.15 | 0.964 m | 15/15 | ~21% / 0.10–0.45 m/s |
| `phase_offset_open.pcd` | 0.60 | 0.559 m | 15/15 | ~21% / 0.27–1.10 m/s |
| `phase_offset_tunnel_w12_l6.pcd` | 0.60 | 0.062–0.069 m | 15/15 | ~25% / 最高 1.50 m/s（饱和） |
| `phase_offset_tunnel_w12_l6.pcd` | 0.15 | **0.143 m** | 15/15 | ~26% / 最高 1.24 m/s |

读法：

- **协同意图现在是真在动的**：`g_coord` 峰值能打到 `g_max = 1.5 m/s` 饱和，
  说明密度/排斥/阻尼三项确实在出力（改之前密度项恒为 0）。
- **k_rho 越大，编队压得越紧**：无障碍图 0.6 → 0.559 m，0.15 → 0.964 m，
  0 → 1.293 m；隧道里同样从 0.062 m 抬到 0.143 m。
  原因是 `rho_0` 把"可见邻居全部放在标称间距"当作参考，非均匀队形的真实密度
  天然低于它，`gamma = 7` 又把这点偏差放大成持续吸引，所以编队会一路收缩到
  平均间距接近 d* 为止。0.15 是把"协同要有可见作用"和"别把编队压扁"折中的值。
- `beta` 有效比例 ~21–25% 是正常的：起飞前和到点后没有 tube bundle，
  `beta` 无效时 SPH 输出按设计关闭（`valid=false`），飞行段内是有效的。

### 3.1 严格 A/B：旧实现 vs 新实现（同一轮、同一探针、同一场景）

做法：把 `sph_intent.h/.cpp` 和 `agent_state_neighbor_runtime_node.cpp` 临时换回
HEAD（= 上一轮真正跑过的旧实现，`h=10 / rest_density=1e6 / k_rep·1/d`），
重新编译后跑同一张图、同一批目标点、同一个只读探针，跑完立即还原并用 md5 校验
还原一致（已校验）。

| 场景 | 旧实现（HEAD） | 新实现（论文版，k_rho=0.15） |
|---|---|---|
| 1.2 m×6 m 隧道 | 最小机距 **0.081 m**，到点 **14/15** | 最小机距 **0.143 m**，到点 **15/15** |
| 无障碍图 | 最小机距 **0.825 m**，到点 15/15 | 最小机距 **0.964 m**，到点 15/15 |
| `g_coord` 幅值特征 | 几乎每个有效样本都顶到 `g_max=1.5`（开关式饱和） | 0.10–1.24 有梯度，只在贴身时才饱和 |
| 到点后是否还有协同力 | 有（`1/d` 在标称间距处仍输出） | 无（标称间距处三项都严格为 0） |

结论：**论文版在两项指标上都更好**——隧道里最小机距 0.081 → 0.143 m（约 1.8×），
而且不再丢机（旧版 14/15）；无障碍图 0.825 → 0.964 m。旧实现唯一的"优点"是
在标称间距处也一直在推，看起来更像"有力"，代价是力永远是饱和大小的开关信号，
既不连续也会持续扭曲队形。

每个 case 只改一个 launch 默认值，其余完全相同，跑同一个探针。基线 =
`h=2.0, d*=1.5, d_rep=0.9, gamma=7, k_rho=0.15, k_rep=1.2, k_damp=1.0, g_max=1.5`。

| 改动 | 场景 | 最小机距 | 到点 |
|---|---|---|---|
| 基线 | 无障碍图 | 0.964 m | 15/15 |
| `h=1.5` | 无障碍图 | 0.908 m | 15/15 |
| `h=2.5` | 无障碍图 | 0.920 m | 15/15 |
| `gamma=3` | 无障碍图 | 0.990 m | 15/15 |
| `k_damp=3.0` | 无障碍图 | 1.033 m | 15/15 |
| 基线 | 1.2 m 隧道 | 0.143 m | 15/15 |
| `d_rep=1.2, k_rep=2.0` | 1.2 m 隧道 | 0.143 m | 15/15 |
| `k_damp=3.0` | 1.2 m 隧道 | 0.130 m | 15/15 |

读法：**围绕当前取值，参数在 ±50% 内变动，结果都落在同一条带里**
（无障碍 0.91–1.03 m，隧道 0.13–0.14 m），说明这些数不是刀尖上的值，
没有"再调一调就能不撞"的近邻更优点。

各参数出处（避免和 SPH-planning 混淆）：

| 参数 | 现取值 | 出处 |
|---|---|---|
| `h` | 2.0 | 自定（论文约束 `d* < 2h`；邻居管理器只给 2.45 m 内邻居）。实测不敏感 |
| `reference_spacing` | 1.5 | **不是常数**：= `formation_spacing`，orchestrator 自动跟随 |
| `d_rep` | 0.9 | 自定（论文约束 `0 < d_rep < d*`，取 0.6·d*）。实测不敏感 |
| `gamma` | 7.0 | **沿袭**旧代码/SPH-planning 的 7；论文只要求 `gamma>0` |
| `k_rho` | 0.15 | **实测标定**（唯一真正调过的增益） |
| `k_rep` | 1.2 | 自定（旧代码 1.0/1.1 属于另一种公式，不能沿用）。实测不敏感 |
| `k_damp` | 1.0 | 自定（旧代码 `k_fri=1.5` 是绝对速度阻尼，公式不同） |
| `g_max` | 1.5 | **沿袭**旧值，未调；下游 allocator 会再裁到 `u_delta<=0.80`、`u_w<=0.40` |

也就是说：**"参考 SPH 的"只剩 `gamma` 和 `g_max` 两个，其余要么由编队/论文约束决定、
要么是实测标定的**。SPH-planning 的 `h=10 / rest_density=1e6 / k_rep(1/d) / k_fri`
不能直接搬——它们属于另一套公式，搬过来正是这次密度项恒为 0 的原因。

### 3.4 pillar 上做 SPH 参数扫描（场景冻结：spacing 1.5 / init_y 20 / 目标 -38）

| case | 最小机距 | 间距 <0.5 m 的采样占比 | 到点 |

| 基线 `k_rho=0.15` | 0.007 / 0.028 m（两次） | 29% | 15/15 |
| `k_rho=0.00` | **0.188 m** | 14% | 15/15 |

| 旧实现（HEAD） | 0.018 m | — | 15/15 |

   就在 0.19 m 附近。

### 3.5 为什么 `k_rho` 会持续压编队：ρ0 的定义偏差（量化）

用真实编队（15 机、spacing 1.5、邻居半径 2.45 m）直接算标称构型下的 η：

```
agent  n_vis  rho    rho0   rho/rho0   eta
    0      6   3.836  3.836   1.000     0.00
    1      6   3.249  3.836   0.847    -0.69
    2      5   3.149  3.363   0.936    -0.37
   ...    ...   ...    ...     ...      ...
    7      3   1.782  2.418   0.737    -0.88
    8      4   1.913  2.891   0.662    -0.94
   ...   (eta: min -0.94  mean -0.69  max 0.00)
```

`rho_0 = 1 + sum_j Wbar(d*/h)` 假设"所有可见邻居都坐在标称间距 d* 上"，
但真实编队里每台机的可见邻居距离分布是 1.5 / 1.86 / 2.4 m 混合，
于是**除了中心机，每台机一出发就被判成"局部稀疏"，持续受到吸引**。
这就是 `k_rho` 越大越压扁、`k_rho=0` 立刻变好的原因——它根本不是增益没调好，
而是参考密度的定义问题。

两条路：

- **短期**：受限场景把 `sph_k_rho` 调到 0（或 0.05），必要时 `sph_d_rep=1.2 /
  sph_k_rep=2.4`。代价是丢掉论文里的凝聚（吸引）支，"集群意图"在开阔空间几乎不动。
- **正确修法（推荐）**：把 `rho_0` 改成"编队标称构型下每台机自己的密度"——
  场景生成器知道编队几何，按 agent 算好 `rho_0_i` 传给 provider（`sph/reference_density`，
  0 = 回退到当前公式）。这样标称队形下 `eta ≡ 0`，`k_rho` 可以回到论文量级而不再压扁编队，
  而且压缩时才排斥、稀疏时才吸引，正是论文的语义。

### 3.6 已实现：按论文定义注入 per-agent rho_0（2026-09-12）

实现（4 处改动，无新门控）：

1. `swarm_orchestrator.py`：新增 `cubic_kernel_weight()` /
   `nominal_reference_densities()`，用**标称编队初始位置**按
   `rho_0_i = 1 + sum_j Wbar(d*_ij/h)` 逐机计算；截断半径取
   `min(2h, neighbor_enter_radius)`，与运行时邻居管理器实际给出的邻居集一致
   （否则 ρ0 会把 provider 看不到的邻居算进去，偏差照旧）。
2. 生成的 child launch 里逐机写入 `<arg name="sph_reference_density" value="..."/>`
   （同时显式传 `sph_h`，保证 orchestrator 和 provider 用同一个 h）。
3. `phase_offset_agent.launch`：新增 `sph_reference_density` arg → `~sph/reference_density`。
4. `sph_intent.h/.cpp`：`SphParameters::reference_density`（>0 直接用，0 回退旧估计），
   `validate()` 要求非负。

15 机圆盘算出来的 ρ0：`3.836, 3.249, 3.149, 3.149, 3.249, 3.149, 3.149, 1.782,
1.913, 1.922, 1.913, 1.782, 1.913, 1.922, 1.913`（中心机 3.836，边缘机最低 1.782）——
和手算完全一致，标称队形下 `eta ≡ 0`。

测试：C++ 单测 11/11（新增"显式 ρ0 ⇒ 标称构型 η≡0、压缩才排斥、稀疏才吸引"，
以及"旧估计在混合环编队下有 −0.69 量级偏差"两个用例）；Python 契约测试 6/6
（顺带修好了上一轮遗留的 `agent_count`/`formation_spacing` 键缺失导致的红灯）。

| 1.2 m 隧道 | 0.143 m | 0.086 / 0.100 m（两次） | 0.131 m |
| `g_coord` 峰值 | 恒受吸引（0.27–1.10） | 无障碍 0.20–0.31、受限段 1.50（饱和） | ~0.01–0.08 |

结论：论文 ρ0 让**标称队形不再被压扁**（无障碍图恢复到 1.34–1.49 m，接近 1.5 m 标称），
pillar 从 0.007–0.028 m 抬到 0.116 m；`g_coord` 变成"标称时安静、被压时才出力"
（无障碍 0.2–0.3 m/s，隧道/柱阵饱和 1.5 m/s），正是论文的语义。隧道里
0.086–0.100 m 与旧估计的 0.143 m 处于同一噪声带（该场景 5 次测量范围
0.062–0.143），仍是几何主导。

### 3.7 ρ0 改完之后再做一轮参数扫描（确认"是否已最优"）

ρ0 换了定义后 `k_rho` 的含义就变了（只在偏离标称密度时才出力），所以要重测：

| 改动 | 场景 | 最小机距 | <0.5 m 采样占比 | 到点 |
|---|---|---|---|---|
| 基线 `k_rho=0.15` | 无障碍图 | 1.344 m | 0% | 15/15 |
| `k_rho=0.05` | 无障碍图 | 1.326 m | 0% | 15/15 |
| `k_rho=0.30` | 无障碍图 | 1.243 m | 0% | 15/15 |
| `h=1.5` | 无障碍图 | 1.256 m | 0% | 15/15 |
| 基线 `k_rho=0.15` | pillar | 0.116 m | 16% | 15/15 |
| `k_rho=0.05` | pillar | 0.034 m | 22% | 15/15 |
| `k_rho=0.30` | pillar | 0.011 m | 17% | **14/15** |
| 基线 `k_rho=0.15` | 1.2 m 隧道 | 0.086 / 0.100 m | 13–17% | 15/15 |
| `d_rep=1.2, k_rep=2.4` | 1.2 m 隧道 | 0.076 m | 16% | 15/15 |

读法：

- **无障碍图上参数已经"平"了**：`k_rho` 在 0.05→0.30（6 倍）之间变化，最小机距只从
  1.326 变到 1.243 m，而且全程 0 次贴近、都 15/15 到点。这就是 ρ0 修好后的预期结果——
  编队不再被参数牵着走。
- **pillar 上单次运行的最小机距噪声极大**（同一配置两次可以差 4 倍：0.007 vs 0.028），
  所以那里应该看 `<0.5 m` 的采样占比：0.05→22%、0.15→16%、0.30→17%，并且
  `k_rho=0.30` 还掉了一台到不了（14/15）。**0.15 在这两个指标上都是最好的点。**
- **隧道对短程排斥不敏感**：`k_rep` 翻倍 + `d_rep` 0.9→1.2，最小机距 0.086→0.076 m，
  在噪声带内。再次印证那儿是 authority/几何主导。

仍然"没调过"的：`gamma=7`（沿袭旧代码，论文只要求 >0，且与 `k_rho` 是乘积耦合）、
`k_damp=1.0`（只在旧 ρ0 下测过一次 3.0，噪声内）、`g_max=1.5`（沿袭，且下游
allocator 会再裁到 `u_delta≤0.80`、`u_w≤0.40`，杠杆很低）。

### 3.8 把协同 authority 加大（`u_w` / `u_delta`）——实测反而更差

先看硬约束：相位速率窗口 `[0.02, 3.0] w/s`、`gvf/cmd/vel_max = 2.0 m/s`、
`u_w_rate_max = 2.0`。当前标称 `ẇ ≈ 1.2 w/s`，所以 `u_w=0.40` 只给了 ±33% 的行程量，
**数值上确实还有余量**。实测结果：

| 配置 | 隧道最小机距 | 隧道 <0.5 m | pillar 最小机距 | pillar <0.5 m | 无障碍最小机距 | 到点 |
|---|---|---|---|---|---|---|
| 基线 `u_w=0.40, u_delta=0.80` | 0.086–0.100 m | 13–17% | 0.116 m | 16% | 1.344 m | 15/15 |
| `u_w=0.80, u_delta=0.80` | **0.020 m** | 19% | **0.020 m** | 21% | — | 15/15 |
| `u_w=0.80, u_delta=1.60` | **0.014 m** | 19% | **0.018 m** | 25% | 1.246 m | 15/15 |

结论：**加大 authority 让受限场景一致性变差**（隧道 0.086→0.014，pillar 0.116→0.018，
`<0.5 m` 采样占比全线上升），无障碍图不变（1.246 vs 1.344，噪声内）。
到点率全是 15/15，`GOVERNOR_INVALID_HOLD` 计数基本不变（隧道 167→167→167，
pillar 167→172→172），所以**不是"加权限把状态机搞坏了"，而是它本身就是负收益**。

推测机制（未单独验证）：纵向权限变大后，飞机能在路径参数 `w` 上大幅刹车/加速，
反而更容易挤到同一段 `w`（同一横截面）上；横向能用的只有 tube 半宽，
而 `u_delta` 翻倍只会让参考横向甩得更快、跟踪滞后带来的瞬时贴近更明显。

因此建议**保持 `u_w=0.40 / u_delta=0.80` 不动**。若还要继续压近距离，
该动的是分离策略（例如把 `u_w` 做成非对称：只允许减速）或加硬分离约束，
而不是继续放大这对上限。

### 3.9 尝试并否决：把 `u_w` 单向化（只允许减速）

按"分离策略"的思路实现过一版：在 adapter 里把 `g_des` 沿切向的正分量夹到 0
（即协同意图只能让参考变慢、不能推快），并加了 `u_w_positive_max` 开关。
**该方案被否决并已完整回退**（代码里已无 `u_w_positive_max`），理由：
相位通道在论文里是双向的（`g_i^coord` 是二维向量，经局部切映射分解成
`(u_w, u_delta)`），减速用于让后机不撞前机、加速用于让前机提速拉开与后机的间距；
单向化会给整条编队的推进加一个系统性偏置，且与论文描述不符。

当前状态：`u_w ∈ [-0.40, +0.40]` 双向对称，与 3.8 节的基线完全一致
（回退后复测无障碍图 1.151 m、0 次贴近、15/15 到点，与 1.344 m 基线同带）。

那条有界排斥——而它在 0.9 m 以外严格为 0，等于留了一条死区。实测表现就是
无障碍图编队一路被压到 1.15 m 才被拉回来（`g_coord` 峰值只有 0.20–0.31 m/s）。

把 `d_rep` 抬到 1.4 m（仍满足论文 `d_rep < d* = 1.5`，且"标称处为 0、一低于标称就出力"）：

| `d_rep` / `k_rep` | 无障碍图最小机距（逐 5 s） | 隧道 | pillar |

想要更硬的"弹性带"可以把 `sph_k_rep` 调到 2.0（无障碍图 1.399 m），但受限场景未验证。

### 6.7 "在障碍物里感觉不到排斥力"——对照实验

把三项协同增益全部置零（`k_rho = k_rep = k_damp = 0`，于是 `g_coord ≡ 0`），
其余链路完全不动，在同一 pillar 场景跑一次：

| 配置 | 最小机距 | <0.5 m 占比 | 到点 |
|---|---|---|---|
| 协同**开启**（定稿，6 次） | 0.002–0.162 m | 11 / 16 / 17 / 24 / 12.8 / 29.5 %（中位 ≈16.5%） | 15/15 |
| 协同**关闭**（`g_coord ≡ 0`，1 次） | 0.016 m | **24.3%** | 15/15 |

关掉协同的结果落在开启区间之内 ⇒ **在这个柱阵场景里，协同对结果没有可测量的影响**。
观察是对的。机制上有两层原因：

1. **力算出来了但执行不出来**：机间协同只有两个执行自由度——横向 δ（受 tube 半宽
   裁剪，且速率上限 0.8 m/s）和沿程相位（±0.40 w/s）。柱阵要过 2.1–4.4 m 的缺口，
   而 15 台 1.5 m 间距的编队足迹约 6 m，几何上必须压缩；实测 `g_coord` 在柱阵里
   确实打到 1.5 m/s 饱和，说明意图在，是**执行容量**不够。
2. **障碍物侧本来就没有"排斥力"这一项**：本工程避障由
   planner 安全路径（ESDF + `safe_distance`）+ tube 横截面硬裁剪（δ 出不去就停在
   边界，即"容不下就按最大边界走"）+ recenter 弹簧（`delta_tracking_gain=3.0`）
   共同保证。论文里"障碍物影响协同"的机制是 β（tube 越窄越衰减吸引支），
   这一项已实现并在飞行段有效（β 峰值 1.0）。但**没有任何一项是"墙把飞机推开"的力**。

若确实要"在障碍物中体现排斥力"，有三条路：

- **软势垒**：用 preview 的横截面区间构造一个障碍物势，δ 越靠近 tube 边界越被推回
  中心线（替代现在的硬裁剪边界行为），仍在 tube 内，安全性不变；
- **硬分离约束**：命令层机间/墙距投影，唯一能在 2 m 级缺口里真正拉开距离的做法；
- **接受现状**：论文框架本身就把避障交给 planner/tube，SPH 只负责机间协调。

### 6.8 机间排斥力在障碍物里体现不出来——根因与修复（2026-09-12）

**根因**：adapter 里有一段"recenter 让位"逻辑（M4I 时为修"到点不回中"加的）：

```cpp
const bool recenter_owns_transverse =
    runtime_ != nullptr && runtime_->recenterRequested();
... if (!recenter_owns_transverse && ...) { g_des += g_coord; }
```

而 `recenterRequested()` 只要 `|delta| > tol` 就置位，并且**一直保持到 delta 回到 0**。
插入探针实测（pillar 场景，15 台，1168 个采样）：

```
recenter_owns=1 : 51%   recenter_owns=0 : 48%
协同被允许时 |delta|：中位 0.013 m, p75 0.041 m
协同被掐掉时 |delta|：中位 0.000 m, p75 0.000 m
```

也就是说：机间协同有一半时间被静音，剩下的一半时间里 real 现的横向位移也只有
1–4 cm——力算出来了（`g_coord` 在柱阵里打到 1.5 m/s 饱和），但落不到 δ 上。

**修复**：去掉这个开关，恢复论文语义
`g_i^des = sat(g_i^coord) − k_rec·delta_i·N_i`（回中项是弹簧，不是静音开关）。
当初促使加它的"到点不回中"问题由到达判据自己解决（判据已按 `|delta| + slack` 放宽），
所以不再需要它。

**效果**（同一套定稿参数，只改这一点）：

| 场景 | 改前（有让位） | **改后** |
|---|---|---|
| pillar 默认场景 | 0.002–0.162 m，<0.5 m 占比 11–30% | **0.167–0.298 m，占比 3.2 / 6.4 / 6.4 / 6.6 %**（4 次） |
| 1.2 m 隧道 | 0.045–0.143 m，13–19% | **0.263 m，12%** |
| 无障碍图 | 1.15–1.34 m，0% | 1.342 m，0% |

到点：4 次 pillar 里 3 次 15/15、1 次 14/15（那次日志显示它是在**收到目标前**的
启动期 hold，`d_goal=38 m`，属于目标发布时序，不是协同导致的卡死）；
隧道、无障碍图均 15/15。

测试：`phase_offset_matched_adapter_test` 10/10、`phase_offset_shadow_adapter_test` 13/13、
`phase_offset_active_adapter_test` 6/6、`sph_intent` 11/11、Python 契约 6/6，整仓编译通过。

### 6.9 tube 空间利用率：`delta_tracking_gain` 3.0 → 1.5（2026-09-12）

执行参考是 `r = p(w) + N·delta`，所以"回中弹簧" `delta_tracking_gain` 直接决定协同
能留住多少横向空间。插桩实测（`preview.envelopeAt(w)` 给出该处 tube 区间，与实际
delta 同时记录）：

```
delta_tracking_gain = 3.0（原值）  n=1269 |delta| 中位 0.017 p90 0.081 max 0.495
                                   tube 区间宽度 中位 1.80 m  贴边比例 1.7%
delta_tracking_gain = 1.5          n=1332 |delta| 中位 0.046 p90 0.234 max 0.873
                                   tube 区间宽度 中位 1.83 m  贴边比例 5.0%
```

即：柱阵里走廊平均有 1.8 m 宽，而 δ 只有 1.7 cm、位置停在正中间（相对位置中位 0.50），
**tube 空间基本没被利用**——卡点是回中弹簧，不是 tube 太窄（隧道里贴边 18.7%，
因为那里走廊窄到 0.52 m）。

扫描结果：

| `delta_tracking_gain` | pillar 最小机距 | pillar <0.5 m | 到点 | 隧道最小机距 | 隧道占比 |
|---|---|---|---|---|---|
| 3.0（原值） | 0.167–0.298 m（4 次） | 3.2–6.6% | 15/15 ×3, 14/15 ×1 | 0.263 m | 12% |
| **1.5（新定稿）** | 0.134 / 0.309 m | 9.0 / 1.3 % | **15/15, 15/15** | **0.304 m** | 12.1% |
| 1.0 | **0.030 m** | 4.8% | **14/15** | 0.112 m | 15.5% |

结论：**1.5** 把 tube 利用率提到约 3 倍（δ 中位 ×2.7、p90 ×2.9、贴边 ×3），
而机间距/到点率与 3.0 无统计差异；1.0 过头（δ 飘、1 台未到点、两张图最小机距都掉），
说明这套"弹簧 + 协同"存在一个最优区间，1.5 在其中。

注意：单机链（`bspline_race` 自己的 test_gvf.launch）仍保留 3.0；
集群链通过 `phase_offset_agent.launch` 的
`phase_offset_manual_delta_tracking_gain` 单独设成 1.5。

### 6.10 在 1.5 的新状态下重测 authority 与 SPH 增益（2026-09-12）

因为回中弹簧换成 1.5（δ 能真正跑起来），旧结论需要复核：

| 变体（dtg 固定 1.5） | pillar 最小机距 | pillar <0.5 m | 到点 | 隧道最小机距 | 隧道 <0.5 m | 到点 |
|---|---|---|---|---|---|---|
| **定稿**（auth 0.40/0.80, `k_rep=1.2`） | 0.083–0.309 m | 1.3–9.0% | 15/15 ×3 | 0.304 m | 12.1% | 15/15 |
| authority ↑（0.80/1.60） | **0.007 m** | **13.2%** | **14/15** | 0.083 m | 8.4% | 15/15 |
| `k_rep` ↑（2.0） | 0.295 m | 3.3% | 15/15 | **0.012 m** | **20.6%** | **14/15** |

两条结论都与旧状态一致：

- **authority 不要加大**：pillar 反而更集中（0.007 m、13.2%、丢 1 台到点）。
  权限只决定"能推多快"，推的方向和时机来自 g_coord；权限变大后协同在拥挤处
  更猛地横推/加速，反而互相挤压。
- **`k_rep` 不要加大**：pillar 持平，但隧道明显变差（0.012 m、20.6%、丢 1 台）。

因此 SPH 与 authority 维持 6.1/6.2 的定稿值，不需要因为 `delta_tracking_gain`
的变化而重调。

关于"最小机距变小"：pillar 上该指标噪声极大（同配置 0.03–0.31），
判断应看稳定的 `<0.5 m` 占比——定稿在 dtg=1.5 下为 1.3–9.0%（中位 3.0%），
反而优于 dtg=3.0 的 3.2–6.6%（中位 6.4%）；隧道持平（12.1% vs 12%）。
放松弹簧确实会允许更大的 δ，理论上可能让个别最坏一对更近（用平均换最坏），
这正是"用 tube 空间"的代价，而不是失败。

### 6.11 修掉"卡住"：governor 的 lead 限制不再丢弃候选 + 停滞后重锚相位

排查过程中定位到一类会把飞机**永久卡住**的故障（与 SPH 无关，发生在 governor/相位层）：

1. governor 用相位候选查参考点；相位候选偶尔会比实际进度超前约 2 m
   （实测 `w_after=21.43` vs `progress_w_=19.425`），参考点因此落在飞机前方 2.49 m，
   超过 `gvf/cmd/governor_lead_max = 1.6 m`，**36 个候选全被 lead 限制丢掉**
   → `no_valid_candidate` → `GOVERNOR_INVALID_HOLD`。
2. 另一种表现：候选集不空，但只剩一个"原地不动"的候选（`cmd_dist=0.000`、
   `selected_v_model_norm=0`），飞机停在**离目标 1.59 m** 处（轨迹下标 105/105、
   `remaining_w=0.002`），而停止状态又让这个条件永远维持 → 自锁。

两处修复（都不含新的门控/证书）：

- **lead 限制改为限幅**：候选超出 `lead_max` 时沿同一条射线拉回到 ≤`lead_max`
  再参与评分（新增 `lead_clamped_count` 计数），不再 `continue` 丢弃。
  落后时飞机会以受限速度追赶，而不是原地冻结。
- **停滞后重锚相位**：候选集为空、或最佳候选是"零步长"（<2 cm）持续
  `gvf/cmd/governor_unlock_timeout`（默认 1.0 s）后，失效相位授权
  （`publishAuthoritativePhase(..., false, ...)`）并 `resetGovernorState()`，
  下一 tick 会把相位按飞机当前位置重新投影；打印 `[GVF][GOV_UNLOCK]`。

验证（pillar 默认场景，同一窗口 132 s，按 FSM 自己的 `[POINT_GOAL][REACHED]` 统计）：

| 运行 | `u_w` | 到点 | `GOV_UNLOCK` | 到点距离 |
|---|---|---|---|---|
| 修复前（各 5–6 次） | 0.40 / 0.50 | 0.40: 15/15；**0.50: 5 次里 2 次丢机**（卡在离目标 22 m） | — | — |
| 修复后 fix50_a | 0.50 | **15/15** | 15 | 0.034–0.155 m |
| 修复后 fix50_b | 0.50 | **15/15** | 15 | 0.034–0.282 m |
| 修复后 fix40_a | 0.40 | **15/15** | 15 | 0.030–0.083 m |

注意：现在"到点率"以 FSM 的 `[REACHED]` 事件为准。之前用固定 0.35 m 阈值统计时
会出现"假丢机"（FSM 判到点、探针判没到），因为到点判据是
`0.2 + |δ| + terminal_offset_slack(0.25)`，带偏移停下时会略超 0.35 m。

## 4. 狭窄通道：0.06 m 贴近是几何问题，不是参数问题

1.2 m 宽 × 6 m 长的通道 + 15 台 1.5 m 间距的飞机：

- 通道内同一路径进程处最多只能横向铺开 ±0.6 m（tube 半宽），
- 沿程排队需要 15 × 1.5 = 22.5 m，而通道只有 6 m，
- 协同能用的authority只有横向 ±0.80 m/s、相位 ±0.40 w/s。

三者加起来都塞不下 15 台，所以它们必然在入口互相穿透。
`g_coord` 已经打到饱和 1.5 m/s，说明**瓶颈不在 SPH 增益，而在可达自由度**。

想要"论文里没有碰撞"的效果，只有三条路（按代价排序）：

1. 场景侧：通道内 5–6 台（或把通道加宽到 ~2.4 m），这是最便宜、最诚实的做法；
2. 提高authority：`phase_offset_manual_u_delta_abs_max`（现 0.80）、
   `u_w_abs_max`（现 0.40），代价是参考轨迹偏离中心线更多；
3. 加一层轻量硬分离约束（机间 + 墙距，取饱和/投影，不做证书），
   这是唯一能在 1 m 级通道里真正保证不撞的做法。
